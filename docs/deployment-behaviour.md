# Deployment behavior

The plan runs after `process-parameters` and before `deploy-prereq`, validating scope, ownership, cache, volumes, and domains across the target without writes. Each service repeats live checks before mutation.

Settings and runtime variables are committed together in a patch targeting only the current service, with `skipDeploys: false`. The deployment-ID baseline and request intent are saved before this commit, and the one newly observed scoped ID is tracked. A separate redeploy after a skipped patch can reuse the previous image, so all launches use the complete patch's own deployment. Each new attempt saves a nonsecret GUID in state and sends it as the reserved `PINGUAPPS_DEPLOYMENT_REQUEST` variable. This creates a real configuration change even when the image, sealed values, and credentials already match. Recovery retains that same marker and never blindly resends an uncertain request. Repeat deployment compares desired live settings, variables, secret fingerprints, volume/domain identities, and resource limits. Unchanged ordinary services reuse their successful deployment; finite release jobs intentionally receive a new attempt marker on a new explicit invocation.

Configuration-patch rejections fail immediately. Recovery checks for newly created deployment IDs first; multiple candidates or an unexpected deployment before the recorded request fail rather than following an arbitrary latest deployment. The same timeout budget covers initialization, readiness, and finite completion. No bootstrap workload is launched before the full desired configuration is applied.

A definitively rejected patch clears its request attempt so the next explicit invocation can use a fresh baseline and desired configuration. A legacy attempt explicitly recorded as unsent can receive a new marker and current baseline; changed desired configuration is safe in that state. Sent or uncertain finite attempts retain the strict no-second-execution guard.

For marker-bearing attempts, the candidate's deployment snapshot must contain that exact marker; the returned patch identity must also match its metadata when available. An unrelated same-image operator deployment cannot satisfy the request. The reserved marker name is rejected in AppHost runtime input. Managed variable names are recorded before a request so an ordinary changed-intent retry can remove variables introduced by an uncertain accepted patch. Unchanged cron activation is still checked for scope, status, and the requested image without waiting for its next scheduled execution.

Railway can expose a deployment before its snapshot request marker is readable. Missing scope or association fields are polled for that same candidate ID within the original deployment deadline. A present but incorrect scope, marker, or patch identity fails immediately, even when another field is missing. Timeout or cancellation preserves the sent attempt; polling never issues another configuration request. See [correlation readiness validation](correlation-validation.md) for the observed missing-to-matching transition and regression coverage.

Markerless legacy sent attempts can resume an already recorded exact deployment ID and must still pass the requested-image guard. A sent legacy attempt without that ID requires operator reconciliation; a new candidate discovered from its baseline cannot prove which request created it.

Pending state is saved before configuration writes. Interrupted application retries the recorded service. Destructive external changes cause failure rather than name-based replacement.

Every explicit deployment records a canonical, credential-keyed desired fingerprint and the scoped deployment-ID baseline before its request. A lost response resumes the one new ID or the exact recorded ID, including after output-read failure. Multiple candidates fail. An uncertain sent request with no discoverable ID is not sent again automatically; reconcile the remote execution before changing its record. A changed pending finite workload or rotated control-plane credential also requires reconciliation. Known terminal failure clears the execution attempt for every service kind so a later explicit deployment can intentionally launch a new attempt; a timeout retains the exact ID for resume. Legacy pending finite state without an attempt record fails safely.

Only variable names previously managed by this package are deleted when removed from the AppHost, including sealed variables. Unrelated provider variables remain. Removing registry credentials sends an explicit null configuration value and removes their recorded fingerprint.

Ordinary services must reach `SUCCESS` for the exact launched deployment ID; an explicitly enabled sleeping ordinary service may also report `SLEEPING`. Finite execution always requires `SUCCESS`, `deploymentStopped`, and every instance `EXITED`. Failed/crashed deployments are rejected even if instances have exited. A timeout blocks dependent services; it does not imply that the remote process was stopped. Cron publication requires the exact deployment's `SUCCESS` activation status and `Never` restart, but does not wait for its next scheduled process or provide a finite release prerequisite.

The exact deployment's `meta.image` must also match the requested retained digest. A successful process or service with a different or unproven image cannot satisfy the release prerequisite. An image mismatch preserves the recorded attempt for operator reconciliation; it never blindly requests a second finite execution. Legacy uncertain pending state remains subject to the same recovery rules.

Cron processes must close their connections and exit after each run. Railway does not terminate an overlapping execution automatically; it skips the next scheduled run while the previous process is still active. See [Railway cron execution requirements](https://docs.railway.com/cron-jobs#service-execution-requirements).

Existing PostgreSQL, Upstash, and Bunny publishers participate through `push-prereq`. They remain responsible for provider-specific ownership/output generation. Adapting those packages to the full site allocation contract belongs to the later template integration phase.

Retained images do not reverse database migrations. Rollback eligibility, migration compatibility, worker handover, and release recovery remain release policies composed through completion dependencies.

The core publishes projects/containers, including web apps and workers. Jobs, RabbitMQ, and Dashboard companions add workload-specific configuration. OpenObserve deployment remains outside these packages. See [live validation](live-validation.md) for verified behavior and limitations.
